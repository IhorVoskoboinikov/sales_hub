# SalesHub — замеры

Здесь записаны замеры, о которых говорит `docs/DESIGN.md`: индексы «без / с» (раздел 3, этап 4.9), способы массового UPDATE (раздел 6, этап 5.9) и chaos-тест массовой операции (раздел 14, этап 5.10). Каждый замер воспроизводится командой — цифры ниже получены ею.

## Стенд

- Ноутбук: 12 ядер, 30 ГБ памяти, NVMe; Docker, `postgres:18.6` из `deploy/compose/docker-compose.yml` с `shared_buffers=1GB`, `max_wal_size=8GB`, `maintenance_work_mem=512MB`, `work_mem=32MB`.
- Данные — `make seed-big` (`backend/scripts/seed_big.sql`): 20 организаций, 2 000 пользователей, 300 тыс. компаний, 5 млн контактов, 1 млн сделок, 20 млн активностей в 26 месячных партициях.
- Распределение неравномерное, как в жизни: крупнейшая организация — 1,1 млн контактов; в ней у самого «тяжёлого» менеджера (`sales_rep`) 349 846 клиентов, у самого «лёгкого» — 2 743.

## Проверка «Готово, когда»: `make explain`

`backend/scripts/explain_lists.py` строит запросы всех списков и отчётов **теми же методами `*_query()`, что выполняет API**, для пяти пользователей крупнейшей организации (org\_admin, viewer, team\_lead крупнейшего отдела, менеджеры с наибольшим и наименьшим числом клиентов), включая 101-ю страницу keyset. Каждый запрос — в двух планах: `custom` (под конкретные значения) и `generic` (`plan_cache_mode = force_generic_plan`, так asyncpg может выполнять подготовленный запрос после пяти запусков).

Результат: **224 плана, Seq Scan по большим таблицам — 0.** Типичные времена — доли миллисекунды для списков (`Index Scan` по индексу уровня, в том числе 101-я страница и менеджер с 350 тыс. клиентов), до 50 мс для канбана и редкого поиска, 5 мс для отчёта по воронке и ~250 мс для отчёта по менеджерам у админа организации (E10).

Одно предупреждение — частый поиск, см. E3.

## Замеры индексов

Запуск: `make experiments` (`backend/scripts/experiments.sql`). Каждый эксперимент выполняется в транзакции `BEGIN; DROP INDEX …` (или `CREATE INDEX …`) `; EXPLAIN (ANALYZE, BUFFERS) …; ROLLBACK` — DDL в Postgres транзакционен, поэтому база после замера та же. В рабочей базе так не делают: `DROP INDEX` держит эксклюзивную блокировку, а новый индекс к заполненной таблице добавляют `CREATE INDEX CONCURRENTLY` (раздел 9).

Время — `Execution Time` из `EXPLAIN ANALYZE`, кэш тёплый.

### E1. «Мои клиенты» менеджера — колонка сортировки должна быть в индексе

`WHERE org_id = :org AND owner_id = :me AND deleted_at IS NULL ORDER BY created_at DESC, id DESC LIMIT 51`

| Индекс | Менеджер с 349 846 клиентами | Менеджер с 2 743 клиентами |
| --- | ---: | ---: |
| `(owner_id, created_at, id)` — выбран | 0,5 мс, `Index Scan Backward` | 0,4 мс |
| `(org_id, owner_id)` из первой версии дизайна | 0,5 мс (планировщик его не взял) | **11 мс**: Bitmap Scan всех 2 743 строк + сортировка |
| нет индекса по ответственному | 0,2 мс | **95 мс**: обход индекса организации, отброшено 24 546 чужих строк |

Вывод. Индекс без колонки сортировки находит строки, но потом читает и сортирует **все** записи менеджера ради 50 штук. Индекс `(owner_id, created_at, id)` отдаёт их сразу в нужном порядке. Неравномерность данных меняет картину: у «тяжёлого» менеджера каждая третья строка организации — его, поэтому даже без индекса нужные 51 находятся мгновенно. Именно поэтому `make explain` проверяет и «тяжёлого», и «лёгкого» менеджера.

### E2. Глубокая страница: OFFSET против keyset

100 000-я строка списка контактов организации:

| Способ | Время | Что читает |
| --- | ---: | --- |
| `OFFSET 100000 LIMIT 51` | 14,6 мс | 100 051 запись индекса (Index Only Scan) |
| keyset `(created_at, id) < (:c, :i)` | **0,2 мс** | 51 запись |

Вывод. OFFSET читает и выбрасывает всё до нужной страницы — время растёт с номером страницы. Keyset начинает с курсора, и 101-я страница стоит столько же, сколько первая.

### E3. Поиск по подстроке (pg\_trgm)

| Запрос | С GIN `gin_trgm_ops` | Без индекса |
| --- | ---: | ---: |
| редкая подстрока `c4242@m` (30 кандидатов) | **26 мс** | 860 мс (параллельный проход по 1,1 млн строк организации) |
| частая подстрока `петренко` (каждый шестой контакт) | **1 130 мс** | — |

Вывод. Триграммы отлично работают для избирательного поиска. Для частой подстроки индекс находит 816 тыс. кандидатов, Postgres читает 140 тыс. страниц таблицы и сортирует 180 тыс. строк организации. Планировщик не может это предвидеть: для `LIKE '%…%'` pg\_trgm оценивает избирательность фиксированно (здесь — 490 строк при 816 тыс. реальных), и увеличение статистики по выражению индекса (`ALTER INDEX … SET STATISTICS 1000`) оценку не меняет — проверено. Обход индекса уровня по порядку с фильтром тоже не спасает: планировщик считает его дорогим, а без битмапа выбирает параллельный Seq Scan (650 мс).

Что с этим делают в жизни:
- поисковый движок — Elasticsearch (этап 9, раздел 17): у него частые слова — обычный случай, а сортировка по релевантности и `LIMIT` дешёвые;
- ограничивают поиск: от 3 букв или цифр подряд (уже так) и, например, только по имени без домена email.

Seq Scan при этом нет — индекс используется, поэтому `make explain` помечает этот запрос предупреждением, а не ошибкой. В seed-данных частота искусственно высокая (6 фамилий на 5 млн контактов), но в жизни так ведут себя, например, домены почты (`gmail`).

### E4. Сегмент по тегу (`tags @> ARRAY['vip']`)

`count(*)` контактов организации с тегом `vip` (165 тыс. строк из 1,1 млн):

| Индекс | Время |
| --- | ---: |
| GIN `(tags)` | 335 мс |
| без индекса | 549 мс: параллельный Seq Scan |

Вывод. GIN по `tags` не знает организаций: Bitmap Index Scan отдаёт 735 тыс. строк с тегом `vip` **всех** организаций, Postgres читает почти всю таблицу (140 тыс. страниц) и отбрасывает 570 тыс. чужих строк фильтром `org_id`. Поэтому выигрыш лишь в полтора раза, и он падает с ростом числа организаций. Индекс по тегам выгоден для редких тегов; для сегментов внутри организации есть составной GIN `(org_id, tags)` через расширение `btree_gin`, а частые сегменты лучше считать фоновой задачей (этап 5).

### E5. Канбан: покрывающий индекс

Итоги открытых сделок воронки по этапам (77 762 сделки):

| Индекс | Время | Как |
| --- | ---: | --- |
| `ix_deals_kanban (pipeline_id, stage_id, id) INCLUDE (title, amount_usd, owner_id, team_id, org_id) WHERE status = 'open' AND deleted_at IS NULL` | **48 мс** | Index Only Scan, `Heap Fetches: 0` |
| без него | 115 мс | параллельный Seq Scan по 1 млн сделок |

Вывод. Все нужные запросу колонки, включая колонки фильтра `Access`, лежат в индексе — таблица не читается вовсе. `Heap Fetches: 0` получается только после `VACUUM`: он заполняет visibility map, без неё index-only scan проверял бы каждую строку в таблице.

### E6. Просроченные открытые сделки

| Индекс | Время |
| --- | ---: |
| частичный `(org_id, expected_close_date, id) WHERE status = 'open' AND deleted_at IS NULL` | **0,05 мс**, Index Only Scan |

### E7. История сделки на партиционированной таблице

| Вариант | Время |
| --- | ---: |
| индекс `(deal_id, created_at, id)` на каждой партиции | **0,8–19 мс** (тёплый / холодный кэш): Index Only Scan по 24 партициям |
| без него | 1 090 мс: проход по всем 20 млн строк |
| вторая страница: только `(created_at, id) < курсор` | 0,28 мс, читаются все партиции |
| вторая страница: плюс `created_at <= курсор` | 0,29 мс, партиции новее курсора отсечены |

Вывод. Индекс на партиционированной таблице — это индекс на каждой партиции; запрос без условия на `created_at` обходит их все (здесь 26), но каждая проверка — один короткий спуск по дереву. Условие `created_at <= курсор` нужно, потому что сравнение строк `(created_at, id) < (…)` Postgres для отсечения партиций не использует; на этой сделке выигрыш мал (её активности разбросаны по всем месяцам), но для «свежих» карточек он отсекает почти все партиции.

### E8. Открытые задачи: частичный индекс

| Индекс | Размер на 20 млн активностей |
| --- | ---: |
| `(owner_id, due_at, id) WHERE done_at IS NULL` | **64 МБ** |
| такой же без `WHERE` | 949 МБ |

Список открытых задач менеджера с 350 тыс. клиентов — 1 мс по всем партициям. Вывод: открытых задач 5%, поэтому частичный индекс в 15 раз меньше полного, быстрее обновляется и лучше помещается в кэш. Это работает потому, что «открытая» — ровно `done_at IS NULL` (у записанных звонков и писем `done_at` ставится сразу, раздел 3).

**Побочный замер — раздувание индексов.** Размеры выше — на чистой базе. После `make seed-big-clean` (DELETE 26 млн строк) и повторной загрузки тот же частичный индекс занимает 124 МБ, а btree `(deal_id, created_at, id)` — 1 710 МБ вместо 882 МБ: `VACUUM` помечает освободившиеся страницы индекса для повторного использования, но не возвращает их и не уплотняет дерево. Поэтому для «перезалить всё» лучше `make clean && make up` (тома с нуля); в рабочей базе — `REINDEX CONCURRENTLY`, а старые месяцы активностей удаляются целыми партициями (`DETACH` / `DROP`), без раздувания.

### E9. BRIN по времени

«Все активности за неделю» (без фильтра по организации):

| Индекс | Время |
| --- | ---: |
| нет (отсечение партиций оставило один месяц) | 88–145 мс, Seq Scan одной партиции |
| BRIN `(created_at)` | **54–57 мс** |

Размер BRIN на 20 млн строк — **648 КБ**, для сравнения btree `(deal_id, created_at, id)` — 882 МБ. Вывод: BRIN хранит минимум и максимум на группу страниц и полезен, только когда строки лежат на диске в порядке времени (seed вставляет каждый месяц `ORDER BY created_at`, как они и копились бы). Партиции уже дают грубое отсечение по месяцу, BRIN уточняет до недели. В API он не используется — оставлен экспериментом.

### E10. Отчёт по ответственным: materialized view

Тот же запрос, что строит `ReportRepository.managers_query` (открытые, выигранные и проигранные за год по каждому ответственному), для админа крупнейшей организации:

| Источник | Время | Что читает |
| --- | ---: | --- |
| `deal_stats` (materialized view) | **252 мс** | 45 465 строк агрегата организации |
| прямой `GROUP BY` по `deals` | 1 164 мс | 221 422 живых сделки |
| `REFRESH MATERIALIZED VIEW CONCURRENTLY deal_stats` | 7,4 с | все 1 млн сделок |

Вывод. View выигрывает в 4–5 раз, но не в сотни: он сгруппирован по ответственному, отделу, воронке, этапу, статусу **и месяцу**, поэтому в крупной организации в нём десятки тысяч строк. Отчёт по воронке читает из него за 5 мс, а отчёт по менеджерам — за четверть секунды. Если этого мало, следующий шаг — отдельный, более грубый view под этот отчёт (ответственный × статус × месяц). Цена любого view — отставание на интервал обновления (с этапа 5 — задача beat каждые 5 минут) и 7 секунд работы базы на каждое обновление. `CONCURRENTLY` дольше обычного `REFRESH`, но читатели отчёта в это время не ждут.

## Замеры способов UPDATE (этап 5.9)

Запуск: `make bench-updates` (`backend/scripts/bench_updates.py`), без параметров — все замеры на 1 млн и 5,47 млн строк по одному разу, ~2 часа. Часть замеров — через `BENCH`, например `make bench-updates BENCH="--methods U3,U7 --volumes 1m"`; все параметры (размеры чанков и пачек, интервал пробника, число повторов) — `uv run python scripts/bench_updates.py --help`. Цифры ниже — из двух прогонов 26.10.2026: `BENCH="--volumes 1m --repeat 3"` (U1, U7, HOT и трижды U2–U6 на 1 млн, 89 мин) и `BENCH="--methods U2,U3,U4,U5,U6 --volumes 5m"` (73 мин). Все числа, планы и размеры копии печатает сам скрипт.

### Как устроен замер

- **Свежая копия на каждый замер.** Перед каждым замером `contacts` заново копируется в `bench_contacts` (`LIKE contacts INCLUDING ALL` без индексов, потом те же девять индексов: PK, четыре btree уровня и компании, частичный `UNIQUE (org_id, email)`, корзина и два GIN — триграммы и теги; FK `owner_id → users` — `LIKE` его не копирует, а при смене ответственного Postgres проверяет его на каждой строке). Копия 5 469 646 строк — 2,9 ГБ, ~1,5 мин (строки 10 с, индексы 72–78 с, `VACUUM (ANALYZE)` 3–5 с). Так каждый замер начинается с одного состояния: только что загруженная таблица, плотно заполненные страницы, кэш прогрет (страницы копии только что прочитаны `VACUUM`). Первая версия скрипта мерила всё подряд на одной копии; каждый замер раздувал и перемешивал её для следующего (2,9 → 7 ГБ), и на той же операции это давало +15 % времени и +25 % WAL — цифры зависели от порядка способов. В конце копия удаляется — и при ошибке, и по Ctrl+C / SIGTERM. `contacts` не меняется: `n_tup_upd` до и после обоих прогонов одинаковый (588 270).
- **Что меняется.** То же, что в чанке передачи клиентов: `owner_id`, `team_id`, `version + 1`, `updated_at` — и, как в передаче, только живые строки (`deleted_at IS NULL`): 980 040 из первого миллиона id, 5 369 300 из всей таблицы. U2, U3 и U7 выполняют тот же `BulkRepository.reassign`, что воркер, U7 строит границы тем же `BulkRepository.chunk_bounds`, что `bulk.plan`. Каждый замер передаёт записи **новому** пользователю: ключи индексов действительно меняются.
- **Перед замером** — `CHECKPOINT`, **после** — `VACUUM (ANALYZE)` (его время — в таблицах). Метрики: время, WAL (`pg_wal_lsn_diff`), полные образы страниц (FPI, `pg_stat_wal.wal_fpi`), число чекпоинтов за замер, `n_tup_hot_upd` и `n_dead_tup`, самый долгий чанк. Автоочистка копии выключена.
- **Пробник** — отдельная сессия, как ручная правка карточки: каждые 100 мс берёт случайную живую строку **из тех, что массовая операция меняет прямо сейчас** (текущий чанк или пачка; у U1, U2 и U5 — весь сегмент), пробует `SELECT … FOR NO KEY UPDATE NOWAIT` и, если строка занята, делает обычный `UPDATE`, который ждёт. Так видно, сколько правок **действительно ждали** блокировку и сколько; задержка остальных (сброс WAL при `COMMIT`, диск) считается отдельно — у всех способов это p99 до 0,1–0,3 с. В первой версии пробник правил случайную строку всего сегмента и почти не попадал в текущий чанк — его p99 был в основном задержкой диска, а не блокировкой.
- **Повторы.** U2–U6 на 1 млн — по три раза, каждый раз в другом порядке. Разброс времени — **до 2 %**, WAL — до 0,3 %; поэтому одиночные замеры (U1, U7, HOT, 5,47 млн) с разницей меньше ~5 % значимыми не считаем.

Стенд — как выше (раздел «Стенд»): ноутбук на AMD Ryzen 5 5500U (6 ядер / 12 потоков), 30 ГБ памяти, NVMe. Postgres 18.6 из compose (`shared_buffers=1GB`, `max_wal_size=8GB`, `maintenance_work_mem=512MB`, `work_mem=32MB`; по умолчанию `checkpoint_timeout=5min`, `synchronous_commit=on`, `full_page_writes=on`, `wal_compression=off`). Во время прогонов был запущен только контейнер Postgres — воркеры, beat и API не работали. Каталог `pg_wal` держался на 7–8 ГБ (`max_wal_size`), диска хватило с запасом (свободно ~71 ГБ).

#### U1. ORM в цикле — 10 000 строк, экстраполяция

Первые 10 000 id (9 816 живых строк); для сравнения на тех же строках и тоже сразу после `CHECKPOINT` — U3 одним чанком: так в отношении нет разницы объёма и полных образов страниц.

| Вариант | Время | Строк/с | Запросов | Во сколько раз медленнее чанка | На 1 млн | На 5,47 млн |
| --- | ---: | ---: | ---: | ---: | ---: | ---: |
| U3 одним чанком на те же строки | 0,75 с | 13 172 | 1 | — | — | — |
| U1a: объекты одним `SELECT`, правка в цикле, один commit | 5,0 с | 1 963 | 9 817 | в 6,7 раза | ≈ 8,5 мин | ≈ 46 мин |
| U1b: `get` → правка → commit на каждую строку | 22,0 с | 446 | 19 632 | в 30 раз | ≈ 37 мин | ≈ 3,4 ч |

- SQLAlchemy не склеивает такие UPDATE в один: у `Contact` есть `version_id_col` и `eager_defaults`, поэтому на каждую строку — свой `UPDATE … WHERE id = :id AND version = :v RETURNING updated_at` с проверкой `rowcount`. U1b — так выглядит «вызвать сервис одной записи в цикле».
- **С пробником U1a сорвался:** между `SELECT` и `UPDATE` пробник успел поменять 9 строк из 9 816, SQLAlchemy получил `StaleDataError` (`expected to update 9816 row(s); 9807 were matched`) и откатил всю пачку после 4,7 с работы; цифра в таблице — повтор без пробника. Длинное «прочитать всё → поменять в памяти → записать» с оптимистической блокировкой проваливается от любой параллельной правки. U1b в этом прогоне конфликтов не получил: между `get` и `commit` одной строки проходят миллисекунды.
- WAL на строку у всех трёх — ~12 КБ против 2,4 КБ на миллионе: на 10 000 строк сразу после `CHECKPOINT` почти каждое изменение страницы — первое, то есть полный образ страницы.

#### U2. Один UPDATE на всё

Скорость та же, что у чанков, — 14,4 тыс. строк/с. Но все строки блокированы до `COMMIT`: ручная правка ждала 62–66 с на миллионе и **6 минут** на всей таблице — до конца операции. Ошибка в конце откатывает всё, прогресса не видно. Ещё одна цена, которую замер не показывает: всё это время транзакция держит горизонт `xmin`, и `VACUUM` не может убрать мёртвые строки ни в одной таблице базы. Граница «до ~50 тыс. строк» из таблицы раздела 6 — это ~3,5 с блокировки (столько длится чанк в 50 тыс., см. U3).

#### U3. Чанки по id BETWEEN

- Чанк в 10 000 строк даёт ту же скорость, что один UPDATE (на 2–3 % медленнее на миллионе, разница — на грани разброса), а ручная правка ждёт не дольше одного чанка: max 0,63–0,93 с при самом долгом чанке 0,8–1,0 с.
- Чанк в 1 000 — на 7–12 % медленнее (5 470 транзакций — 5 470 сбросов WAL на диск при `COMMIT`), зато ожидание правки — до 0,16 с на миллионе и 0,5 с на всей таблице.
- Чанк в 50 000 по скорости не лучше 10 000 (разница — в пределах разброса), а правку держит до 3,2–3,8 с.
- Чем крупнее чанк, тем реже правка вообще застаёт свою строку заблокированной (чанк — малая часть сегмента), но тем дольше ждёт, если застала: для 10 000 ждала каждая четвёртая правка из тех, что попали в текущий чанк, — остальные успевали до того, как чанк до неё дошёл, или после его `COMMIT`.

#### U4. UPDATE FROM unnest

13,6–13,8 тыс. строк/с — на 4–7 % медленнее чанков, хотя у каждой строки своё значение (здесь чётные id — одному пользователю, нечётные — другому). 10 000 id в одном параметре-массиве, план — Nested Loop по первичному ключу (печатает скрипт); блокировки — как у чанка того же размера (max 0,7–0,9 с). Время чтения id в Python в замер не входит: в этом сценарии значения уже есть у приложения.

#### U5. COPY в staging + UPDATE FROM

`COPY` быстрый: 0,4 с на миллион строк и 2 с на 5,47 млн (временная таблица не пишет WAL). Дальше — один `UPDATE`, то есть те же блокировки, что у U2: правка ждала 66–68 с на миллионе и 6–8 минут на всей таблице.

На миллионе планировщик выбирает Merge Join (staging сортируется по id, строки копии читаются по первичному ключу) — скорость и WAL как у U2. На 5,47 млн он сам выбрал Hash Join, и замер стал самым медленным: 10,6 тыс. строк/с и **вдвое больше WAL** — 26,9 ГБ против 13,2 ГБ. Причина — полные образы страниц: **2,7 млн FPI против 0,53 млн** и 5 чекпоинтов вместо 2. Hash Join с `work_mem = 32MB` делит обе таблицы на батчи по хешу id, поэтому строки идут в случайном порядке; одна и та же страница меняется много раз в разные промежутки между чекпоинтами, и после каждого чекпоинта первое изменение снова пишет её целиком. Тот же `UPDATE` с `enable_hashjoin = off` (Merge Join, порядок id) — 373 с и 13,2 ГБ, как U2. Это подтверждает решение для импорта (раздел 6): merge переносит из staging чанками по `row_no`, а не одним `UPDATE`, — блокировки короткие, а каждый чанк настолько мал, что его порядок строк на WAL почти не влияет.

#### U6. SQLAlchemy update(Model) со списком dict-ов

`session.execute(update(Model), [{"id": …, "owner_id": …, "team_id": …}, …])` — bulk UPDATE по первичному ключу: asyncpg выполняет один подготовленный `UPDATE … WHERE id = $1` на каждый dict (executemany). Это 8,9–9,0 тыс. строк/с — **на 60 % дольше** чанков, но в 4,5 раза быстрее U1a: объекты не создаются, `RETURNING` нет. Две особенности:

- с `version_id_col` (как у `Contact`) этот режим берёт `version` из dict как условие `WHERE version = :v`: передача `version + 1` даёт `StaleDataError`, а любая параллельная правка строки откатывает всю пачку. Поэтому U6 идёт через модель без `version_id_col` (`BenchContactPlain` в скрипте) и `version` не меняет: выражение `version + 1` в этом режиме не записать — только готовые значения. Это выяснено отдельной ручной попыткой при написании скрипта, в прогон она не входит;
- значит, для «одно значение на весь сегмент» лучше U3, для «своё значение на строку» — U4: та же идея пачек, но одним запросом на пачку.

#### U7. Границы чанков: по строкам или равными диапазонами id

Чанки — `BulkRepository.reassign` с `WHERE owner_id = :from AND deleted_at IS NULL AND id BETWEEN …`, по 10 000 строк или id; каждый вариант — на свежей копии. Время включает нарезку. Для равных диапазонов «нарезка» — это `min(id), max(id)` записей менеджера.

Крупнейший `sales_rep` seed-данных: 349 846 строк в диапазоне id 5 100 002…6 217 369 (диапазон своей организации, 1,1 млн id; каждый третий id — его):

| по строкам (`chunk_bounds`, как `bulk.plan`) | 35 | 9 846 / 10 000 / 10 000 | 260 мс | 27,8 с | 12 570 | 953 мс |
| равные диапазоны по 10 000 id | 112 | 2 285 / 3 127 / 3 239 | 993 мс | 29,7 с | 11 794 | 404 мс |
| равные диапазоны, 35 чанков (число — как по строкам) | 35 | 9 815 / 9 989 / 10 159 | 954 мс | 27,8 с | 12 585 | 887 мс |

Синтетический менеджер: каждый 50-й контакт таблицы — 107 412 строк, разбросанных по всем 5,47 млн id (так выглядят клиенты, которых менеджер набирал годами, пока id росли у всех организаций); его копия строится сразу с этим ответственным, без UPDATE:

Вывод.
- Шаг в 10 000 id у разбросанного менеджера даёт **547 чанков по ~200 строк** (заполнены на 2 %) — та самая оценка «~500 почти пустых чанков» из раздела 6. Каждый чанк — задача Celery, строка `bulk_job_chunks`, транзакция и `COMMIT`; здесь, без воркеров, это уже **+29 % времени** (14,3 с против 11,1 с), а с очередью цена каждого чанка ещё выше. У «тяжёлого» менеджера плотность выше (каждый третий id), и шаг по id дал 112 чанков по ~3 тыс. строк — +7 % времени.
- Равные диапазоны с числом чанков «как по строкам» на seed-данных дали те же ~10 000 строк в чанке: записи каждого менеджера разложены по своему диапазону id равномерно. Но этот способ всё равно требует знать число строк, а с неравномерным распределением (например, 100 тыс. клиентов, полученных одним импортом, — подряд идущие id, — плюс старые клиенты, разбросанные по таблице) чанки вышли бы разного размера. Такого менеджера в seed нет, и этот случай **не замерен** — это рассуждение. Нарезка по строкам даёт ровно `BULK_CHUNK_SIZE` строк при любом распределении — поэтому `bulk.plan` делает именно её.
- Цена нарезки зависит от способа по-разному. `chunk_bounds` читает только частичный индекс `(owner_id, created_at, id)` (Index Only Scan) — время пропорционально числу строк менеджера: 80 мс на 107 тыс., 260 мс на 350 тыс. `min(id), max(id)` планировщик ищет по первичному ключу с двух концов таблицы, отбрасывая чужие строки фильтром, — время зависит от того, где лежат записи: у разбросанного менеджера свои строки есть у обоих концов (3–7 мс), у «тяжёлого» они в начале таблицы, и поиск `max` проходит 4,3 млн чужих id (~1 с). Для `bulk.plan` и то и другое — разовый запрос на job.
- Разбросанные строки дороже: 9,7 тыс. строк/с против 12,6 тыс. и **19 КБ WAL на строку** против 3,6 КБ — каждая строка на своей странице таблицы, поэтому страниц меняется (и попадает в WAL полным образом: 247 тыс. FPI на 107 тыс. строк) в разы больше. Чанк в 10 000 таких строк длится до 1,1–1,5 с.

### HOT: SET owner_id против SET source

Последний 1 млн id (989 170 живых строк), чанки по 10 000 (`UPDATE … WHERE id BETWEEN`). Две копии, разница между которыми — только `fillfactor`: обычная (100, как `contacts` после загрузки) и загруженная сразу в таблицу с `fillfactor = 90` (2 882 МБ против 3 020 МБ, +5 %). На каждой — два замера, каждый на свежей копии.

| Что меняем | fillfactor | Время | Строк/с | WAL | HOT-обновлений | VACUUM |
| --- | ---: | ---: | ---: | ---: | ---: | ---: |
| `SET source` — колонка без индекса | 100 | 64,2 с | 15 417 | 2,49 ГБ | 3 212 (0,3 %) | 5,4 с |
| `SET owner_id, team_id` — как reassign | 100 | 66,1 с | 14 970 | 2,47 ГБ | 4 | 5,6 с |
| `SET source` | 90 | **56,3 с** | 17 560 | **2,30 ГБ** | **114 555 (11,6 %)** | 5,0 с |
| `SET owner_id, team_id` | 90 | 67,8 с | 14 580 | 2,50 ГБ | 358 | 4,9 с |

Вывод.
- HOT (heap-only tuple) — обновление, при котором новая версия строки остаётся на той же странице и **индексы не трогаются**. Условия два: не меняется ни одна индексированная колонка, и на странице есть место.
- **Передача клиентов не бывает HOT никогда:** `owner_id` и `team_id` входят в индексы уровня, поэтому каждая строка — новая версия плюс новая запись в каждом индексе, условию которого строка подходит (у живой строки — 8 из 9: индекс корзины частичный, `WHERE deleted_at IS NOT NULL`), включая оба GIN (их ключи не изменились, но новая версия лежит по другому адресу). Это и есть основная цена bulk — ~2,4 КБ WAL и ~70 мкс на строку, — и от способа UPDATE она не зависит.
- Колонка без индекса на плотных страницах HOT почти не даёт: после `make seed-big` (и после `COPY` при импорте) страницы заполнены на 100 %, места под новую версию нет — HOT у 0,3 % строк, время и WAL — как у reassign.
- С `fillfactor = 90` HOT — у 11,6 % строк (свободных 10 % страницы хватает на несколько новых версий, дальше страница заполняется): на 12 % быстрее и на 8 % меньше WAL, чем тот же `SET source` на обычной копии, и на 17 % быстрее того же reassign на копии с `fillfactor 90`. Для `contacts` это пригодилось бы ручным правкам неиндексированных полей (телефон, источник, статус) — не массовой передаче. Сейчас `fillfactor` не меняем: таблица станет на 5 % больше, а выигрыш скромный и только у правок неиндексированных колонок; если `n_tup_hot_upd` в `pg_stat_user_tables` покажет, что их много, — кандидат на будущее (`ALTER TABLE … SET (fillfactor = 90)` действует только на новые страницы, старые перепишет `VACUUM FULL` или `pg_repack`).

### Выводы

1. **Скорость у всех set-based способов почти одна — 13,5–14,5 тыс. строк/с** (U2, U3, U4, U5 на 1 и 5,47 млн, разброс повторов — до 2 %). Время уходит внутри Postgres — новая версия строки, восемь индексов, проверка FK, ~2,4 КБ WAL на строку, — а не на запросы между приложением и базой. Поэтому способ выбирают по блокировкам, длине транзакции и восстановлению после сбоя, а не по скорости. Медленнее только построчные: U6 (executemany) — 9 тыс. строк/с, ORM в цикле — 0,45–2 тыс.
2. **Чанки — основной способ, 10 000 строк — правильный размер (`BULK_CHUNK_SIZE`).** Они так же быстры, как один UPDATE (на 2–3 % медленнее), а ручная правка ждёт не больше одного чанка (до 0,9 с) вместо всей операции (минута на миллионе, 6 минут на всей таблице). Каждый чанк — своя транзакция: прогресс виден, сбой откатывает один чанк, а `VACUUM` может убирать уже выполненные. Чанк в 1 000 строк — минус 7–12 % скорости, в 50 000 — не быстрее, но держит правку до 3,8 с.
3. **Один UPDATE (U2) и COPY + один UPDATE FROM (U5)** — только для небольших объёмов: блокировка всех строк до конца. У U5 на больших объёмах планировщик может выбрать Hash Join — случайный порядок строк, вдвое больше WAL и на 35 % дольше.
4. **Своё значение на строку — `UPDATE … FROM unnest`** (U4) пачками: скорость и блокировки почти как у чанков.
5. **ORM в цикле — никогда для объёма**: в 7–30 раз медленнее чанка на тех же строках, а с оптимистической блокировкой (`version_id_col`) длинная пачка проваливается `StaleDataError` от любой параллельной правки. Bulk `update(Model)` со списком dict-ов — терпимо по скорости (+60 % времени), но `version` не увеличить выражением.
6. **Границы по строкам**, а не равными диапазонами id: при разбросанных записях равные диапазоны дают сотни почти пустых чанков (547 по 200 строк) и +29 % времени уже без очереди. Нарезка по строкам стоит пропорционально числу записей менеджера (сотни миллисекунд), `min/max` — от расположения записей, от миллисекунд до секунды.
7. **Объём WAL** — ~2,4 ГБ на миллион переданных строк (до 19 КБ на строку, если строки разбросаны): передача 100 тыс. клиентов — 0,25–2 ГБ WAL, это нагрузка на реплики и бэкапы. `VACUUM` после переписывания всей таблицы — 20–40 с.

Что не замерено: разброс одиночных замеров (U1, U7, HOT, 5,47 млн — по одному разу; оценка — по разбросу повторов на 1 млн), менеджер с неравномерным распределением id (в seed такого нет), влияние долгой транзакции U2 / U5 на очистку других таблиц (горизонт `xmin`), холодный кэш (все замеры — сразу после построения копии).

## Chaos-тест (этап 5.10)

Запуск: `make chaos` (`backend/scripts/chaos.py`) против стенда `make up`, без параметров — оба сценария, ~22 мин (до шага 5.15 — ~21); один сценарий — `make chaos CHAOS="--scenario a"` (~1 мин) или `"--scenario b"`; остальные параметры (`--contacts`, `--kill-at`, `--no-hold`, `--redelivery-wait`, `--down-seconds`, с шага 5.15 — `--mailpit`, `--telegram-chats`) — `uv run python scripts/chaos.py --help`. Код выхода 1, если хоть одна проверка не прошла или kill промахнулся — промах тоже проверяется (см. «Как устроен»), а не выводится из того, что job не успела закончиться. ### Как устроен

- **Свои данные.** Скрипт создаёт организацию `chaos-<id>`, отдел и `org_admin` (пароль хэшируется тем же `hash_password`, что у приложения), на каждый сценарий — двух менеджеров (`sales_rep`; с шага 5.15 — и своего `org_admin`-автора job, см. «Уведомления» ниже) и прежнему **100 000 контактов** одним `INSERT … SELECT FROM generate_series` (7,4–7,8 с, в прогонах 4 и 5 — 10,8–12,5 с; id подряд в конце таблицы, `version = 1`). Вход — настоящий `POST /auth/login`, запуск — `POST /bulk/reassign-owner` (`include = ["contacts"]`), итог ещё раз читается `GET /bulk-jobs/{id}`. Seed-данные не трогаются; в конце (и при ошибке, и по Ctrl+C / SIGTERM) удаляется всё созданное — 200 тыс. контактов, job с чанками, 2 строки журнала, люди, отдел, организация — и `VACUUM (ANALYZE) contacts` (4–5 с). Число контактов и `max(id)` после прогона — те же, что до него (в прогонах 26.10 — 5 469 646 и 10 569 646, в прогонах 4 и 5 — 5 372 781 и 10 569 646); `make up`-стенд остаётся запущенным.
- **Как попасть в середину чанка.** Чанк в 10 000 строк идёт ~1 с, вся job без сбоев — ~3 с: пока скрипт дождался бы `processed > 30 %` и спросил `celery inspect` (~2 с на вызов), job бы уже закончилась. Поэтому до запуска job скрипт берёт в своей транзакции `SELECT … FOR UPDATE` одной строки в середине каждого чанка начиная с 4-го (`--hold`, по умолчанию). Чанки 0–3 проходят (`processed = 40 000`), четыре процесса пула берут чанки 4–7, проходят в своём `UPDATE` половину строк и ждут блокировку — у каждого открыта транзакция с 5 000 изменёнными строками. Тогда скрипт убивает процесс (A) или весь воркер (B) и сразу отпускает блокировку. Держать её дольше `soft_time_limit` чанка (60 с) нельзя — чанк упал бы по таймауту, поэтому её отпускает и сторож через 40 с; на деле от начала ожидания до kill проходит ~5 с. `--no-hold` — kill по времени, без гарантии попасть в чанк (см. «Наблюдения»).
- **PID** — из `celery inspect stats` (процессы пула) и `inspect active` (какой процесс выполняет какой чанк этой job: `worker_pid` и `args`), вызванных через `docker compose exec worker-bulk` с адресатом `bulk@$HOSTNAME`, как в healthcheck. Одного `stats` мало: он не говорит, какой процесс сейчас в чанке.
- **Попадание kill проверяется.** Три вызова `inspect` идут ~5 с, чанк — ~1 с, так что ответ мог устареть. Поэтому прямо перед kill скрипт проверяет, что строки этих чанков в `bulk_job_chunks` ещё `pending` (транзакция не закоммичена) и что столько же запросов воркера стоят в `pg_stat_activity` за соединением блокировки (`pg_blocking_pids`) — они в своём `UPDATE`; пока блокировка держится, закоммитить эти чанки нельзя, проверка не устаревает до kill. Убивается только чанк, в диапазоне которого есть строка под блокировкой; если число чанков не совпало с `--chunk-size` (у стенда другой `BULK_CHUNK_SIZE`) — промах сразу. В B после kill неподтверждённые сообщения читаются из hash `unacked` — убиты ровно они. После прогона — по логам: убитый в A чанк выполнен заново **тем же сообщением** (`bulk_chunk_done` того же `task_id` после kill, не `bulk_chunk_already_finished` — иначе kill попал между коммитом и подтверждением, промах).
- **Уведомления (с шага 5.15).** У каждого сценария свой автор job (`org_admin` `chaos-<id>-A-author@chaos.example`) и получатель — новый менеджер; оба с подтверждённым email и умолчаниями настроек. После финала job — в B уже после повторной выдачи исходных сообщений, то есть и после повторного finalize копиями чанков, — скрипт ждёт писем (до 60 с) и публикации outbox организации, ещё 10 с и проверяет через HTTP API Mailpit стенда (`/api/v1/search?query=to:"…"`, `/api/v1/message/{id}`): автору ровно одно письмо «Масову операцію завершено — SalesHub» со строкой «Оброблено записів: 100000 з 100000.», получателю — ровно одно «Вам передано клієнтів — SalesHub» со строкой «Вам передано клієнтів: 100000 (контакти — 100000).»; в базе одно событие `bulk_job.completed` этой job и по строке `sent_notifications` на письмо. Telegram — только при `TELEGRAM_BOT_TOKEN` у воркера стенда и `--telegram-chats AUTHOR,RECIPIENT` (Bot API настоящий: придуманному чату он ответит «chat not found»); проверка — строки `sent_notifications` канала telegram, привязки целы, нет `failed_tasks` `send_telegram`. В конце письма этих адресов удаляются из Mailpit, outbox организации и `sent_notifications` её людей — из базы.
- **Таймлайн** — из трёх источников: действия скрипта, строки базы (`started_at`, `finished_at` чанков и job, рост `reaps`) и `docker compose logs` воркеров и Postgres (выдача сообщения по `task_id`, `bulk_chunk_done`, `bulk_chunk_already_finished`, `bulk_job_reaped`, гибель процесса пула, откат транзакции убитого процесса).

`task_reject_on_worker_lost` работает, как описано: главный процесс Celery видит гибель процесса пула и сразу возвращает сообщение в очередь (reject с requeue), пул заменяет процесс (`[10, 12, 13, 167]` → `[10, 12, 167, 204]`), строки `failed_tasks` нет. Из 1,6–1,7 с восстановления ~0,55–0,6 с — до повторной выдачи сообщения и ~1 с — само выполнение чанка заново, целиком (1,0–1,05 с от выдачи до `bulk_chunk_done`). Повторная выдача во всех трёх прогонах пришла сразу (за 1–50 мс) вслед за подтверждением других чанков под блокировкой (5–7 доделывают вторую половину ~0,5 с после того, как её отпустили): в прогоне 1 — после всех трёх, в прогонах 2 и 3 — после двух; в прогонах 4 и 5 — так же, за 10–14 мс после подтверждения чанка 7, только сами чанки под блокировкой доделывались дольше (~1 с — стенд медленнее), отсюда и +1,1–1,3 с до повторной выдачи, и ~1,8 с на выполнение чанка заново. Похоже, consumer забирает возвращённое сообщение, когда подтверждения других задач будят его цикл опроса Redis; причину глубже не разбирали — без `--hold` (других ждущих чанков нет) эта цифра может быть другой. Ожидание отката транзакции убитого процесса на `claim` — 0–0,1 с: в прогоне 1 сообщение пришло за 0,1 с до отката, в прогонах 2 и 3 — уже после него (см. «Наблюдения»).

### Что проверялось и как

Во всех прогонах обоих сценариев — все проверки зелёные (кроме проверки логов в B прогона 4 — ошибка скрипта, см. ниже; строки «по логам» и «kill попал» — с прогона 3, «уведомления» — с прогона 4):

| Проверка | Как |
| --- | --- |
| job завершилась | `status = done`, `error IS NULL`, `failed_chunks = 0`, `failed_rows = 0`; `GET /bulk-jobs/{id}` — 200, `done`, 100 000 / 100 000 |
| `processed == total` | и оба равны **числу созданных контактов** (100 000). Одного `processed == total` мало: чанк ставит `total = GREATEST(total, processed)`, и дважды посчитанный чанк поднял бы оба числа вместе |
| ни один чанк не посчитан дважды | 10 строк `bulk_job_chunks`, все `done`; сумма `rows` == `processed`; у каждого чанка `rows` == реальному числу строк его диапазона id у нового ответственного |
| ни одна строка не изменена дважды | у всех 100 000 контактов `version = 2` (создан с 1, каждый `UPDATE` чанка — `version + 1`). Повторный `UPDATE` того же диапазона ничего не находит (`owner_id = :from`) — проверка подтверждает это на данных, а не на коде |
| у старого 0, у нового все | `count(*)` по `owner_id`: 0 и 100 000 |
| итог записан один раз | `result = {"rows": {"contacts": 100000}}` и ровно одна строка `audit_log` `bulk_job` этой job с теми же `rows` |
| упавших задач нет | 0 строк `failed_tasks` с этой job в `args` |
| ничего не придёт потом | ни одного сообщения убитых чанков в `unacked` и в очереди `bulk`; в B — после их повторной выдачи и подтверждения |
| каждый чанк выполнен один раз — по логам | ровно один `bulk_chunk_done` на номер чанка, с `rows` как в базе (`rows=0` повторного `UPDATE` не прошёл бы). Лог пишется до коммита, поэтому строка убитой задачи до kill не считается — её транзакцию откатил Postgres; убитые чанки выполнены после kill |
| kill попал в транзакцию чанка | перед kill — `pending` и запросы воркера за блокировкой скрипта; в A — `bulk_chunk_done` того же `task_id` после kill и нет `bulk_chunk_already_finished`; в B — у копий `bulk_chunk_already_finished` и нет `bulk_chunk_done` |
| ровно одно уведомление каждому (шаг 5.15) | Mailpit стенда: автору одно письмо с итогом («Оброблено записів: 100000 з 100000.»), получателю одно «Вам передано клієнтів: 100000 (контакти — 100000).»; одно событие `bulk_job.completed` на job и по строке `sent_notifications` канала email на письмо — автору и получателю. В B — через 20 минут после финала, когда копии чанков ещё раз вызвали finalize: второго события и второго письма нет. Telegram — не проверялся: у стенда нет `TELEGRAM_BOT_TOKEN` (скрипт так и пишет) |

### Найденные ошибки

#### Номер попытки в логе reaper на единицу больше

В первом прогоне B база показала `reaps = 1`, а строка лога — `bulk_job_reaped reaps=2 chunks=4`. Причина: `BulkService._resend_chunks` (и `_resend` для pending и импорта) писал в лог `job.reaps + 1` **после** `mark_reaped`, а ORM-`update()` с `synchronize_session` по умолчанию сам переносит `reaps + 1` в объект `job`, загруженный в той же сессии, — единица прибавлялась дважды. На логике это не сказывалось (решения reaper читают `reaps` из базы под `FOR UPDATE`), но врал лог, по которому разбирают зависшие job. Исправлено: номер попытки берётся до `UPDATE`; в `test_bulk_reaper.py` тесты правил (1) и (3) проверяют `reaps` в строке `bulk_job_reaped` (без исправления падают). Во втором прогоне — `reaps=1`.

#### Лог убитого контейнера терялся, если `up -d` создавал его заново (прогон 4)

В прогоне 4 у B не прошла одна проверка — «в логах ровно один `bulk_chunk_done` на чанк»: строк чанков 0–3 не было вовсе. Все остальные проверки, включая письма, — зелёные. Причина — в скрипте, а не в приложении: конфигурация compose поменялась после создания контейнера worker-bulk (переменные Telegram шага 5.11), и `docker compose up -d` после kill создал новый контейнер (главный процесс снова `pid 7`), а `docker compose logs` показывает только текущий — строки чанков, выполненных до kill, пропали вместе со старым. Исправлено: в B скрипт читает лог убитого контейнера сразу после отпускания блокировки, до `up -d` (`kill_logs`), и объединяет его с текущим без повторов. Прогон 5 — все проверки зелёные.

#### Время писем: получатель — через 1,2–1,3 с после автора

Во всех четырёх сценариях прогонов 4 и 5 письмо автору приходит через 0,06–0,08 с после финала job, а получателю — через 1,25–1,28 с. Это `rate_limit='50/m'` у `notifications.send_email` (раздел 15): воркер выдерживает между задачами одного типа 60 / 50 = 1,2 с. Так и задумано.

### Наблюдения

- **Транзакция убитого процесса живёт до конца своего запроса.** Postgres замечает, что клиента нет, только когда снова к нему обращается: backend убитого процесса дождался блокировки, доделал свой `UPDATE` (вторую половину чанка, ~0,5 с) и лишь потом, получив EOF, откатил транзакцию — всё это время он держал строку чанка `FOR UPDATE` и половину строк контактов. Если повторно выданный чанк приходит раньше отката, он ждёт на `claim` (строка чанка `FOR UPDATE` без `SKIP LOCKED`) и после отката выполняет чанк целиком — так и задумано (раздел 6, шаг 4). На стенде это ожидание почти не видно: в прогоне 1 — 0,1 с, в прогонах 2 и 3 откат случился раньше, чем пришло сообщение. Без `--hold` оно не больше остатка чанка (<1 с); у долгих запросов его укорачивает `client_connection_check_interval` (Postgres 14+) — для чанков не нужен.
- **Без `--hold` kill промахивается**: `make chaos CHAOS="--scenario a --no-hold"` — job закончилась раньше первого ответа `celery inspect`, скрипт отчитался «ни один чанк job не выполняется — промах» (код 1). С `--chunk-size 5000` на стенде с `BULK_CHUNK_SIZE = 10 000` — сразу промах «чанков 10 (ждали 20)»; блокировки легли не туда, и kill не выполняется. Блокировка не меняет того, что проверяется: убит процесс посреди транзакции чанка, где часть строк уже изменена.

Что не проверено: kill посреди `bulk.plan` (короткая задача очереди `default`). До коммита plan job остаётся `pending` — её подберёт повторно выданный plan или правило (1) reaper через 2 минуты (`test_bulk_reaper.py`). После коммита, но до постановки группы чанков (`group(...).apply_async()` — после коммита) job уже `running` с `pending`-чанками без сообщений: повторный plan ничего не ставит (job не `pending`), правило (1) не подходит, подберёт только правило (3) — через 5 минут без прогресса плюс до минуты до beat и только при пустой очереди `bulk` (`test_plan_lost_before_enqueue_is_resent_only_by_rule_3`). Не проверены и kill главного процесса Celery без контейнера, гибель Postgres или Redis посреди job, `reaps ≥ 3` (`bulk.stuck`) на стенде — только в integration-тестах, импорт CSV (`imports.import_contacts`, своё правило reaper) и одновременная работа двух воркеров bulk. Уведомления `bulk_job.completed` с шага 5.15 проверяются только письмами: Telegram на стенде не проверен — нет токена бота и двух чатов (`--telegram-chats`); путь «ровно одно сообщение в Telegram» проверяет integration-тест `test_bulk_reassign_e2e.py` на подменённом Bot API. Ветка скрипта с `--telegram-chats` (привязка чатов, проверка строк `sent_notifications` канала telegram, привязок и `failed_tasks` `send_telegram`) поэтому не выполнялась ни в одном прогоне — её ошибки, как и ошибки конфигурации воркера (токен, `TELEGRAM_API_URL`), всплывут при первом запуске с токеном. Убить worker с очередью `notifications` посреди отправки письма (дубль возможен, только если процесс умрёт между ответом SMTP и коммитом, раздел 16) — не проверялось.
